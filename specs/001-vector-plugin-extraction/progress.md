# Progress - Vector Plugin Extraction

## 2025-11-16
- Completed **T001** (`docs/vector-plugin-isolation.md`). Added the migration guide summarizing plugin optionality, prerelease migration paths, missing-plugin diagnostics, CI/test expectations, and troubleshooting so users understand how to install LiteDB.Vector and migrate existing databases.
- Completed **T002** (`scripts/verify-vector-clean.ps1`). Implemented the ripgrep-based guard that scans LiteDB/ for "Vector" references, supports repo-relative allowlists, and exits with an error when vector strings remain outside approved extension points.
- Completed **T003** (`LiteDB/Plugins/Indexing/CustomIndexStrategyDescriptor.cs`, `LiteDB/Plugins/ILitePlugin.cs`, `LiteDB/Plugins/EnsureIndexContext.cs`, `LiteDB/Plugins/DefaultPluginContext.cs`, `LiteDB/Client/Database/LiteDatabaseServices.cs`, `LiteDB.Vector/*`). Generalized the vector strategy descriptor into `CustomIndexStrategyDescriptor`, added `ICustomIndexStrategyRegistry`, renamed plugin context accessors to `CustomIndexes`, updated LiteDB.Vector registrations/tests/scripts/docs, and removed the old vector-specific contract so future plugins can register their own index strategies through the shared registry.
- Completed **T003a** (`LiteDB/Plugins/Indexing/IPluginIndexMetadataRegistry.cs`). Defined the contract types for plugin-owned index metadata serialization, including the registry interface, descriptor, and payload container so future steps can decouple metadata persistence from strategy logic.
- Completed **T004a** (`LiteDB/Plugins/Storage/IPageTypeRegistry.cs`, `LiteDB/Plugins/Storage/PageTypeRegistry.cs`, `LiteDB/Plugins/ILitePlugin.cs`, `LiteDB/Plugins/DefaultPluginContext.cs`, `LiteDB/Engine/Pages/PageFactoryRegistry.cs`, `LiteDB.Vector/VectorSearchPlugin.cs`, docs/tests). Replaced the old opaque page factory registry with the new page-type registry/descriptor/context, added numeric page codes, updated engine plumbing to route buffers through `PageConstructionContext`, and refreshed LiteDB.Vector plus docs/tests to consume the new registration flow.
- Completed **T004** (`LiteDB/Plugins/Bson/CustomBsonTypeDescriptor.cs`, `LiteDB/Plugins/Bson/CustomBsonTypeRegistry.cs`, `LiteDB/Document/BsonType.cs`, `LiteDB/Document/Bson/BsonTypeRegistry.cs`, `LiteDB/Plugins/ILitePlugin.cs`, `LiteDB/Plugins/DefaultPluginContext.cs`). Renamed the BSON registry surface to `ICustomBsonTypeRegistry`, introduced the `CustomBsonTypeDescriptor` delegates, updated the default registry implementation, and rewired core consumers plus docs so plugin-defined BSON handlers register through the new descriptor.
- Completed **T004b–T004d** (`LiteDB/Plugins/Query/ISqlFunctionRegistry.cs`, `LiteDB/Plugins/Query/SqlFunctionRegistry.cs`, `LiteDB/Plugins/Query/IQueryOperatorRegistry.cs`, `LiteDB/Plugins/Query/QueryOperatorRegistry.cs`, `LiteDB/Plugins/Query/IQueryCostModelRegistry.cs`, `LiteDB/Plugins/Query/QueryCostModelRegistry.cs`). Added the SQL function/operator/cost registries with their descriptor types and default implementations so upcoming phases can expose them through the plugin context and planner.
- Completed **T005** (`LiteDB/Plugins/PluginDiagnosticPolicy.cs`, `LiteDB/Plugins/ILitePlugin.cs`, `LiteDB/Plugins/DefaultPluginContext.cs`). Introduced `IPluginDiagnosticPolicy` plus the default implementation scaffold, added the missing-behavior enum, and wired ILitePluginContext with setter/accessor support so plugins can declare how LiteDB should react when plugin assets are accessed without the plugin present.
- Completed **T005a** (`LiteDB/Plugins/ReservedCodeRanges.cs`, `LiteDB/Plugins/Bson/CustomBsonTypeRegistry.cs`, `LiteDB/Plugins/Storage/PageTypeRegistry.cs`, `LiteDB/Plugins/DefaultPluginContext.cs`, `LiteDB/Plugins/Query/*Registry.cs`). Added shared helpers enforcing LiteDB.Vector's reserved code ranges and updated all registries to detect duplicate registrations, throwing `InvalidOperationException` with conflicting plugin details before state is mutated.
- Completed **T006** (`LiteDB/Plugins/ILitePlugin.cs`, `LiteDB/Plugins/DefaultPluginContext.cs`, `LiteDB/Client/Database/LiteDatabaseServices.cs`). Verified the plugin context now instantiates/exposes the diagnostic policy plus SQL function/operator/cost registries and that `LiteDatabaseServices` surfaces these properties so consumers and plugins can resolve them at runtime without reflection.
- Investigated **T006a** and confirmed the LiteDB.Vector plugin still consumes internal engine types such as `BasePage`, `PageBuffer`, `Snapshot`, and `CollectionPage` (see `LiteDB.Vector/VectorIndexStrategy.cs`, `LiteDB.Vector/Engine/Pages/VectorIndexPage.cs`, `LiteDB.Vector/Engine/VectorIndexService.cs`). Removing the `InternalsVisibleTo` declarations currently breaks the build, so the entries remain until the upcoming custom index/metadata/page registry work replaces those dependencies per the plan in `specs/001-resolve-vector-findings/progress.md` (T029).
