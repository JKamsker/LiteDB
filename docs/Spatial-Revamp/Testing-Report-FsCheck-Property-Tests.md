1) Executive Summary
Branch `pr-84-codex-add-fscheck-property-tests-for-litedb.spatial-m14epp` delivers the most coherent pairing of generators and harness coverage: it exercises axis-aligned and convex queries through curated candidate sets while asserting index, covering, and exact-stage behaviour before delegating to oracle checks (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/CartesianBoundingBoxDifferentialTests.cs:13`, `LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/CartesianPolygonDifferentialTests.cs:18`, `LiteDB.Spatial.Core.Tests/TestSupport/Cartesian2DTestHarness.cs:68`). `pr-81-codex-add-fscheck-property-tests-for-litedb.spatial` contributes a well-structured sized generator but its polygon property currently compares LiteDB output against the bounding-box proxy rather than the NTS polygon and masks near-boundary mismatches (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:96`,`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:109`,`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:128`). `pr-82-codex-add-fscheck-property-tests-for-litedb.spatial-w1yac6` shines in diagnostics via a custom FsCheck runner but only exercises a single bounding-box scenario (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/BoundingBoxDifferentialTests.cs:22`). `pr-83-codex-add-fscheck-property-tests-for-litedb.spatial-81ut5t` probes query-plan stages with Fluent assertions, yet its `System.Random`-driven generator breaks shrinking guarantees (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:23`,`LiteDB.Spatial.Core.Tests/Support/CartesianScenarioFactory.cs:12`). The recommended path is to adopt branch `pr-84` as the backbone, backfill generator/scenario diversity inspired by `pr-81`, and upgrade failure replay using the runner infrastructure from `pr-82` while folding in the plan-coverage checks introduced in `pr-83`.

3) Failure Diagnostics Review
Branch `pr-81` captures payloads when assertions throw, persisting domain/query/points to `/tests/failures` (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:59`,`LiteDB.Spatial.Core.Tests/Differential/CounterexampleRecorder.cs:20`). The files include exception stacks but omit the FsCheck replay tuple, so the test log must be consulted for `Replay` output when reproducing. `pr-82` offers the strongest story: the custom runner records initial and shrunk arguments plus both seeds and the FsCheck summary (`LiteDB.Spatial.Core.Tests/TestSupport/FsCheckPropertyRunner.cs:112`). The environment variable `SPATIAL_FSCHECK_SEED` accepts `seed:gamma[:size]`, enabling deterministic reruns. `pr-83` writes failures through `FailureRecordingRunner`, but only the property-level seed argument is captured (`LiteDB.Spatial.Core.Tests/Support/FailureRecordingRunner.cs:47`); when the generator depends on `System.Random`, developers must also supply `FS_CHECK_SEED` so FsCheck emits the same seed list (`LiteDB.Spatial.Core.Tests/Support/FsCheckRunner.cs:37`). `pr-84` wraps each property body with `RunWithSnapshot` so any thrown assertion yields a JSON snapshot, while `SpatialPropertyAttribute` honours `SPATIAL_FSCHECK_SEED=seed,startSize` (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/CartesianBoundingBoxDifferentialTests.cs:23`,`LiteDB.Spatial.Core.Tests/TestSupport/SpatialPropertyAttribute.cs:6`,`LiteDB.Spatial.Core.Tests/TestSupport/FailureSnapshot.cs:9`). The snapshots contain curated payloads (domain, polygon vertices, etc.) but, similar to `pr-81`, they rely on FsCheck’s console replay for the random state.

4) Recommended Strategy
1. Use `pr-84`’s harness, property definitions, and candidate breakdowns as the structural baseline because they already enforce index → covering → exact invariants alongside oracle parity (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/CartesianPolygonDifferentialTests.cs:18`,`LiteDB.Spatial.Core.Tests/TestSupport/Cartesian2DTestHarness.cs:68`).
2. Replace the current generator internals with a sized, query-driven variant inspired by `pr-81` so point density and query spans scale with FsCheck size while still injecting interior/exterior probes (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DGenerators.cs:17`,`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DGenerators.cs:45`). Keep the centroid/outside enrichment from `pr-84` to maintain oracle-friendly samples.
3. Adopt `pr-82`’s `FsCheckPropertyRunner` (or equivalent) to standardise `MaxTest`, start/end sizes, and to persist initial vs shrunk arguments and replay tuples into `/tests/failures` (`LiteDB.Spatial.Core.Tests/TestSupport/FsCheckPropertyRunner.cs:31`). Wire it behind a thin `[Property]` wrapper so the richer diagnostics coexist with `pr-84`’s payload snapshots.
4. Integrate `pr-83`’s plan simulation (`LiteDB.Spatial.Core.Tests/Support/SpatialPlanEvaluator.cs:7`) as an additional assertion inside the harness to ensure every expected hit survives index-range filtering, preventing regressions where the covering stage compensates for poor indexing.
5. Close the gap that allowed `pr-81`’s polygon property to short-circuit by asserting both oracle polygon membership and bounding-box coverage separately, with tolerances reserved only for numeric comparisons that genuinely require them (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:96`).

5) Standard Config Proposal
- Package FsCheck 3.x with `[SpatialProperty]` and route execution through a shared runner that sets `MaxTest=150`, `StartSize=5`, `EndSize=200`, and honours `QuietOnSuccess` for clean CI logs (`LiteDB.Spatial.Core.Tests/TestSupport/SpatialPropertyAttribute.cs:6`,`LiteDB.Spatial.Core.Tests/TestSupport/FsCheckPropertyRunner.cs:31`).
- Establish `SPATIAL_FSCHECK_SEED=<seed>,<size>` as the single replay knob and surface the value in the failure snapshot for faster copy/paste reproduction (`LiteDB.Spatial.Core.Tests/TestSupport/FailureSnapshot.cs:9`).
- Persist failure dossiers under `/tests/failures/<timestamp>-<scenario>.json` that combine the snapshot payload with FsCheck’s original/shrunk arguments so engineers can triage without rerunning immediately (`LiteDB.Spatial.Core.Tests/TestSupport/FsCheckPropertyRunner.cs:127`,`LiteDB.Spatial.Core.Tests/TestSupport/FailureSnapshot.cs:14`).
- Default to sequential execution for these heavier tests, but keep `MaxDegreeOfParallelism=1` in the runner to avoid file-write races when multiple seed reproductions run concurrently.

6) Risks & Mitigations
- Lack of shrinkers across all branches means FsCheck may only deliver large counterexamples; add explicit shrink functions for `CartesianPolygonCase` and `CartesianBoxCase` so hulls and point clouds minimise gracefully (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DGenerators.cs:26`).
- Tolerance filters that drop near-boundary misses risk hiding regressions; limit tolerance usage to distance comparisons and always log the discarded ids for review (`LiteDB.Spatial.Core.Tests/Differential/Cartesian2D/Cartesian2DPropertyTests.cs:128`).
- File-based diagnostics can clash under parallel test runs; ensure snapshot filenames include the FsCheck replay tuple or GUID to guarantee uniqueness (`LiteDB.Spatial.Core.Tests/TestSupport/FailureSnapshot.cs:14`).
- `System.Random` driven generation (as in `pr-83`) undermines reproducible shrinking; adopt FsCheck `Gen` combinators exclusively so shrink trees remain meaningful (`LiteDB.Spatial.Core.Tests/Support/CartesianScenarioFactory.cs:12`).
