1) Executive Summary
The four candidate branches all introduce a spatial-oracle helper project, but they differ dramatically in fidelity and test usefulness. `pr-76` is the only branch that wires the oracles into real parity tests and follows the documented tolerances, yet it still lacks breadth (fixtures are tiny and the environment toggle is all-or-nothing). `pr-73` brings the strongest infrastructure—per-oracle gating, clean adapter interfaces, and richer fixture helpers—but never actually exercises them in tests. `pr-74` and `pr-75` diverge from the requirements, reducing the oracles to area/perimeter helpers or even falling back to Haversine, so they cannot anchor the spatial verification effort.

To get to production quality, we should combine the structural pieces from `pr-73` with the higher-level tests from `pr-76`, discarding the regressions present in `pr-74` and `pr-75`. That merged result will need more fixture depth and a few refactors (per-oracle toggles, skip attributes, fixture formats) before it matches the Epic’s acceptance bar.

3) Recommended Strategy
- Use `pr-76` as the base because it already connects the adapters to real engine tests (retain `LiteDB.Spatial.Core.Tests/Engine/SpatialOracleParityTests.cs` and the supporting adapters under `LiteDB.Spatial.Testing.Oracles/Adapters`).
- Port per-oracle gating and the flexible skip attribute from `pr-73` (`LiteDB.Spatial.Testing.Oracles/OracleEnvironment.cs` and `LiteDB.Spatial.Testing.Oracles/OracleSkipAttribute.cs`), replacing the global boolean toggle and `OracleFact` mechanism in `pr-76` so tests can opt into specific adapters.
- Merge the richer infrastructure pieces from `pr-73`—`LiteDB.Spatial.Testing.Oracles/SpatialPrimitives.cs`, the typed fixture loader, and tolerance helpers—to avoid duplicate models and to keep snapshots under `tests/failures` (`LiteDB.Spatial.Core.Tests/Infrastructure/FixtureLoader.cs`, `LiteDB.Spatial.Core.Tests/Infrastructure/SpatialTolerance.cs`, `LiteDB.Spatial.Core.Tests/Infrastructure/FailureSnapshot.cs`).
- Consolidate fixture packs by taking the union of unique datasets (e.g., `tests/fixtures/geojson_polygons/antimeridian_polygon.json` from `pr-73` plus `antimeridian_strip.json` from `pr-76`) and normalise them to a single JSON schema.
- Discard the changes from `pr-74` and `pr-75`; none of their code paths add coverage we still need, and they would regress predicate support and accuracy.

4) Merge Plan
1. Check out `pr-76` and stage its new project/tests as the working baseline.
2. Overlay `pr-73`’s environment + attribute scaffolding and resolve namespace differences (key conflict: replace `OracleFactAttribute` usages with `[OracleSkip(...)]`).
3. Harmonise the fixture loader/tolerance helpers by choosing the `pr-73` implementation and updating `SpatialOracleParityTests` to use the shared APIs.
4. Merge fixture directories, deduplicating file names and aligning formats (expect manual edits in `tests/fixtures/**/*.json`).
5. Update `LiteDB.Spatial.Testing.Oracles.csproj` to keep net8.0 targeting while adding any missing package references from both branches.
6. Run `dotnet test LiteDB.Tests -f net8.0` and the spatial suite specifically to confirm deterministic results.

5) Risks & Mitigations
- Sparse fixtures still risk false negatives: expand the geodesic pair list (scripted import from GeographicLib samples) before relying on the suite.
- PostGIS helper (`LiteDB.Spatial.Testing.Oracles/Adapters/PostgisOracle.cs:17-52`) assumes a live database; guard all usages with env checks and keep them behind an optional category to avoid CI flakiness.
- The combined fixture schema change may break downstream consumers; document the format in `docs/Spatial-Revamp/3-Oracles-and-Fixtures.md` and add loader unit tests.
- Replacing `[Fact]` with `[OracleSkip]` requires test authors to remember the attribute—add an analyzer or documentation snippet to prevent regression.

6) Open Questions
- Do we need to multi-target the oracle project for `netstandard2.0` to share code with legacy test runners, or is `net8.0` sufficient?
- Should PostGIS differential tests ship with precomputed snapshots instead of requiring a live container in CI?
